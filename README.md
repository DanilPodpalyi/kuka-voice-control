# Голосовое управление манипулятором KUKA

Это мой дипломный проект. Задача была простая по формулировке: я говорю команду по-русски, а манипулятор выполняет её на стенде. Например, «Красный кубик» подводит инструмент к кубику по двум точкам. Дальше отдельными командами можно закрыть захват, переместить объект и отпустить его.

На роботе я проверял и Google, и Yandex. В дипломе итоговым вариантом был Yandex SpeechKit. Большую часть времени я работал через Google: для Yandex требовался токен, и доступ был платным. Сейчас токена у меня уже нет, поэтому в этой сборке по умолчанию Google. Адаптер Yandex остался для истории проекта.

## Быстро проверить

Из корня проекта:

```powershell
python voice_control.py --text "Красный кубик"
python voice_control.py --text "Скорость двадцать пять"
python voice_control.py --text "Открой захват"
```

Для этого достаточно Python. Программа покажет, какое действие получилось из текста. Чтобы проверить микрофон, установите зависимости:

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -r requirements.txt
.\.venv\Scripts\python voice_control.py --mic
```

Enter запускает запись, по умолчанию на три секунды. Такой режим остался от стенда: удобно самому выбирать момент записи и пробовать одну команду за раз. Для готовой записи есть `--wav input.wav`. Формат WAV — моно, PCM 16 бит, 16 кГц. В обоих режимах аудио уходит в выбранный сервис распознавания.

Я развёл три ситуации: сервис ничего не разобрал, текст получился, но такой команды нет, и сам запрос к сервису упал. В режиме микрофона после каждого из этих случаев можно начать новую запись. «Завершить сеанс» закрывает программу, старое слово «Стоп» делает то же самое. Если робот уже выполняет движение, голосовая команда его не прервёт. Аварийный останов остаётся на контроллере.

## Как это собрано

- `voice_control.py` записывает аудио или читает WAV, получает текст и сопоставляет его с командой. Обработчик один для обоих сервисов. Команды я оставил фиксированными: так видно, какое действие соответствует конкретной фразе.
- `stand.json` хранит геометрию моего стенда: центр, домашнюю позицию, точки подхода к кубику и шаги движения. Там же порт, таймаут сокета и параметр сглаживания траектории `$APO.CDIS`. Для другого стенда можно передать свой файл через `--stand-config`. Особенность старой настройки: «вправо» и «влево» меняют X и одновременно поднимают инструмент по Z на 20 мм. Я перенёс это поведение как было в ноутбуке.
- `kuka.py` превращает заданные точки и действия захвата в записи переменных через OpenShowVar. Дальше уже программа KRL на контроллере должна взять эти данные и выполнить движение.
- `denoise/` занимается только звуком. Его можно запустить на WAV отдельно или вставить между записью и распознаванием.

### Скорость

Команду нужно произнести целиком, например «Скорость двадцать пять». Подходят также «Скорость 25» и «Скорость 25 процентов». Допустимы целые значения от 1 до 100.

В старых ноутбуках этот блок был закомментирован. В сборке клиент записывает число в `COM_VALUE1`, выставляет `COM_CASEVAR=3` и ждёт, пока контроллер сбросит эту переменную. Порядок записи и подтверждение проверены на имитаторе. Сброс переменной означает завершение обработки команды по протоколу. Проверить, что KUKA действительно выставляет указанный процент, сейчас можно только с исходной программой KRL и доступом к стенду.

## Зачем здесь отдельное шумоподавление

На стенде модуль работал, но в обычных условиях нам уже хватало обработки, которая была в микрофоне и Windows. Смысл отдельного фильтра был в том, чтобы сохранить эту возможность при переносе на микрокомпьютер. Поэтому в обычном запуске он выключен.

На защите я показывал два варианта одной записи со стороны: робот захватывает, переносит и отпускает объект. В одном варианте я после съёмки обработал звуковую дорожку. Так можно услышать разницу. Точность распознавания команд по этим двум роликам оценить нельзя.

Файлов OpenVINO `.xml` и `.bin` со старого устройства в архиве нет. В сборке я использую стандартную NSNet2 на 16 кГц в ONNX. Старый формат по-прежнему можно открыть при наличии пары файлов и совместимого OpenVINO с `openvino.inference_engine`. Пример обработки спектра и конвертации модели подробно разобран в [материале Intel](https://habr.com/ru/companies/intel/articles/558224/).

```powershell
.\.venv\Scripts\python -m pip install -r requirements-denoise.txt
.\.venv\Scripts\python -m denoise --model models/nsnet2-20ms-baseline.onnx --input input.wav --output filtered.wav
```

После клонирования скачайте `nsnet2-20ms-baseline.onnx` в `models/`. Веса лежат отдельно от Git. SHA-256 файла — `88429b6253600be840ab816f46f466811d20078142fb12bff8cafe2b27bd4ca9`. Модель проверена на десятисекундной записи из проекта. Длительность и формат WAV сохранились. [NSNet2 из репозитория Microsoft DNS Challenge](https://github.com/microsoft/DNS-Challenge/blob/8b87a33b2892f147b5c7ad39ea978453730db269/NSNet2-baseline/nsnet2-20ms-baseline.onnx)

Чтобы использовать её перед распознаванием, добавьте `--denoise-model models/nsnet2-20ms-baseline.onnx` к запуску с `--mic` или `--wav`.

## Что нужно для реального стенда

Подключение включается параметром `--robot-host`. По нему клиент обращается к [OpenShowVar](https://github.com/linuxsand/py_openshowvar). На контроллере нужна программа KRL, которая обрабатывает `COM_CASEVAR`, `COM_LENGTH`, `COM_FRAME_ARRAY`, `COM_VALUE1`, `OUT5` и `OUT6`. В этой сборке её файлов нет. Координаты рассчитаны под старую базу, инструмент и оснастку, поэтому перед движением на другом стенде их нужно сверить.

После переноса проверены разбор команд, обмен с имитатором для команды скорости и локальное шумоподавление. Облачное распознавание и движение реального KUKA в этой сборке повторно не проверялись.
